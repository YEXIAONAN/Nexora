# Nexora

> **v0.1.0-alpha.2 · 内部 Alpha 预览版**
> 面向内部 Alpha 试用，不建议用于生产环境。生产部署与真人团队试用尚未验收；真人试用待真实用户参与，不阻碍内部 Alpha。

Nexora 是一个面向小型研发团队的 Web 协作应用：管理团队、项目与三级任务，分别记录工作进展、交付验收、贡献核定与奖金方案，保留各环节的独立权限和业务证据。

Alpha.2 在账号、邀请和项目协作基础上，加入 **Phase 07 团队开通与结构化进展上报**，以及 **Vue + API 的奖金完整流程**：人工预算与资格、不可变方案版本、独立核定、单独发布、本人结果和模拟发放记录。贡献比例不自动换算金额，模拟发放不执行银行转账。变更与待验事项见 [CHANGELOG](CHANGELOG.md)。

## 1. 我需要安装什么

`./start` 是 Bash 脚本，适用于 macOS/Linux；Windows 推荐使用 WSL。原生 Windows 可运行 Go 后端，但本仓库没有原生 PowerShell 一键启动脚本。Windows PR #13 已整合，真实 `windows-latest` 的 Go 后端构建和测试已通过，证据见 [CHANGELOG](CHANGELOG.md)；不据此承诺原生 Windows 一键启动或完整生产支持。

| 依赖 | 版本 | 用途 |
| --- | --- | --- |
| Docker + Docker Compose v2 | 任意近期版本 | 本地 PostgreSQL 17；外部数据库模式可不安装 |
| Go | 1.26+ | 后端 API（也可用 Docker 方式） |
| Node.js | 22+（CI 基线 24） | 前端 Vite |
| pnpm | 10.x | 前端依赖与脚本 |

首次使用如未安装 pnpm：

```bash
corepack enable
corepack prepare pnpm@10.34.5 --activate
```

## 2. 配置环境

```bash
cp .env.example .env
```

开发环境默认值即可直接运行。需要关注：

- `NEXORA_DATABASE_URL`：本地 PostgreSQL 连接串（默认指向 `nexora` 数据库，账号与密码见 `.env.example`）
- `NEXORA_REGISTRATION_MODE`：`open` / `invite` / `closed`，开发环境默认 `open`
- `NEXORA_API_PORT` / `NEXORA_WEB_PORT`：默认 `8080` / `3000`

`./start` 首次运行发现 `.env` 缺失时会自动从 `.env.example` 创建，并提示你检查配置。

可用 `NEXORA_ENV_FILE=/绝对路径/dev.env ./start` 指定环境文件（相对路径以仓库根目录为基准）；显式指定的文件不存在时直接报错，不创建或加载默认 `.env`。外部数据库请在该文件中设置 `NEXORA_EXTERNAL_DATABASE=1` 和 `NEXORA_DATABASE_URL`，跳过全部 Docker Compose 操作；**仍会对所配置的数据库执行迁移，请先确认目标库**。默认仍使用本地 Compose。`NEXORA_HTTP_ADDR` 可单独决定 API 端口；若同时设置 `NEXORA_API_PORT`，两者端口必须一致。脚本会导出监听地址及 `VITE_DEV_API_TARGET=http://127.0.0.1:实际端口`，Vite 使用严格端口，不会自动换端口。

## 3. 一键启动

```bash
./start
```

它会依次：

1. 启动（或复用）PostgreSQL 容器；
2. 应用尚未执行的数据库迁移；
3. 构建并启动 Go API（仅复用 `/readyz` 数据库与 schema 检查通过的服务）；
4. 从公开 `/api/v1/meta` 确认 ROOT 状态：仅 `true` 显示已初始化，`false` 时交互式安全初始化（无默认密码），无法确认则显示未知；随后启动 Vite；
5. 输出前端地址、API 地址、运行模式和注册策略。

启动成功后访问：

- 前端：**http://127.0.0.1:3000**
- API：http://127.0.0.1:8080
- 存活检查：http://127.0.0.1:8080/healthz；数据库/schema 就绪检查：http://127.0.0.1:8080/readyz

按 `Ctrl+C` 会停止本次启动的 API 与前端。PostgreSQL 容器与数据会保留，第二次运行 `./start` 不会清空账号、团队、项目和任务。

重复执行是安全的：已在运行的 API/前端会被复用，迁移只前进不回滚，不会重建管理员或修改密码。

### 手动启动（可选）

```bash
make env
make dev-db
make migrate-up
make bootstrap      # 仅首次：交互式设置 ROOT 用户名与密码
make dev-api        # 终端 A
make dev-web        # 终端 B，Vite 默认 5173
```

## 4. 第一次创建管理员

- 使用 `./start`：检测到没有 ROOT 时会在终端提示你设置密码；
- 或显式执行：`make bootstrap`。

用户名默认为 `admin`；`./start` 可通过 `NEXORA_ROOT_USERNAME` 指定用户名，直接运行 bootstrap CLI 时使用 `-username` 参数（`make bootstrap` 使用默认用户名）。交互用于安全输入并确认密码，不存在默认密码。使用独立账号登录「用户管理」管理普通用户，不共享 ROOT 凭据；ROOT 是平台管理员身份，不自动获得任何团队、项目或奖金权限。

## 5. 注册第二个用户

开发环境默认开放注册：

1. 打开 http://127.0.0.1:3000/register
2. 填写用户名、显示名称、可选邮箱、密码（至少 10 个字符）
3. 注册成功后回到登录页，用新账号登录

生产环境如需限制注册，设置 `NEXORA_REGISTRATION_MODE=invite`：只有已被团队邀请的用户名才能注册；`closed` 则完全由管理员在「用户管理」中创建账号。

普通注册用户不会获得平台管理员权限，也不能自助创建团队。可把这个第二用户作为团队 Owner；`invite` / `closed` 模式的全新安装可先由平台管理员在「用户管理」创建 Owner 账号。建议用不同浏览器配置或独立会话分别登录，避免混淆角色。

## 6. 创建 Team 并邀请成员

1. 平台管理员进入「团队」，填写「团队名称」，在「团队负责人」选择已存在的活跃用户（例如第二用户），点击「创建团队」；
2. 改用被指定的 Owner 账号登录，进入该团队的「成员与邀请」；创建者 ROOT 不会因创建团队自动加入；
3. Owner（或团队 Admin）在「邀请成员」填写用户名、团队角色和有效期，点击「发出邀请」；
4. 对方如果还没注册，可先邀请：对方用**同一个用户名**注册后，登录并在「邀请收件箱」接受邀请；
5. 接受后可在顶部切换团队，或在「团队」点击「设为当前」。

团队之间数据隔离；同一用户在不同 Team 可以有不同角色（Owner / Admin / Member）。平台管理不绕过团队成员关系与业务授权。

## 7. 创建 Project 与管理项目成员

1. 团队 Owner/Admin 进入当前团队的「项目」，点击「新建项目」；
2. 填写名称、描述，在「项目负责人」选择团队成员担任 lead，点击「创建项目」；Owner/Admin 可任命或交接 lead，但团队管理身份不等于项目管理权限；
3. 使用 lead 账号打开项目工作区的「项目成员」，从「添加 Team 成员」选择已接受团队邀请的成员，点击「添加成员」；lead 可移除项目成员。团队邀请不会自动把成员加入项目。

项目工作区包含「项目概览」「任务树」「项目成员」「里程碑」「进度历史」「项目设置」，以及「贡献核算」「奖金批次」入口。**项目成员和任务由 lead 管理**；ROOT、团队 Owner/Admin 若不是该项目 lead，不隐式获得任务管理权。任务负责人和协作者必须同时具有有效的团队与项目成员资格。

## 8. 分配任务、上报进展与交付验收

### 任务与工作进展

1. lead 在「任务树」点击「新建任务」，创建最多三级的任务，指定父任务（可留空）、负责人、协作者、优先级、权重和截止时间；
2. 负责人或协作者可从「我的任务」进入叶子任务，点击「开始任务」；汇总任务的进度来自后代叶子任务，不单独上报；
3. 在任务详情「工作进展 → 上报本次进展」填写「当前进度」（整数 0–99）与必填「本次工作内容」，按需填写「已完成工作」「下一步计划」「当前问题」「交付证明」，点击「提交进展」。证明支持链接、Commit/PR 引用；进展上报不提供文件附件。

「最近上报进度」是执行者报告的 `actual_progress`，不等于验收；执行中的「汇总有效进度」最高 79%，提交交付待验收为 80%，只有独立验收通过才为 100%。上报记录保留结构化工作说明与证据，不能用拖动进度代替成果提交或完成任务。

### 交付、验收与贡献核定

1. 叶子任务满足提交条件后，进入「交付与验收」页签的「成果与验收」，填写成果说明、证据链接或成果附件，点击「提交新成果版本」；这是独立于「提交进展」的操作；
2. lead 默认可审核；其他成员需由 lead 在「项目成员 → 审核人授权」中「授予审核权」；
3. 审核人填写「审核意见」，选择「通过当前版本」或「驳回当前版本」。提交者不能审核自己的成果；
4. 驳回后查看原因，点击「开始修正」或在「交付与验收」中「进入补正」，修正并重新提交新成果版本。

正式验收后，在「贡献核算」中建立贡献案例、形成草案并完成独立核定。**进展上报、成果验收、贡献核定、奖金核定是不同流程**；贡献核定不自动发奖金，奖金也不改写正式贡献比例。

## 9. 奖金批次：从人工方案到本人结果

完整奖金功能需要 **schema v11**（v9/v10 的奖金路由不启用，返回 404）。以下操作通过真实 Vue 页面与 API 完成，不依赖 mock 数据。

### 创建批次与分配角色

1. 先由 lead 补齐项目成员。具有有效团队与项目成员关系的团队 Owner/Admin 或 lead，进入「奖金批次」，点击「创建奖金批次」；
2. 在「创建独立资金批次」填写「来源标识」（`funding_key`，小写字母、数字、连字符或下划线）、「批次名称」「真实资金来源」和「创建理由」。一个标识对应一笔独立资金，不要为同一资金重复建批次；初始预算为 0；
3. 选择两位**其他活跃项目成员**分别担任「金额负责人」（manager）与「独立核定人」（reviewer）：二者不同，均不能是创建者。核定人还必须独立于方案编辑者、受益人和来源贡献提案核定人；不足成员或存在利益冲突时，先调整人员，不能借 ROOT 绕过。

| 角色 / 入口 | 能做什么 |
| --- | --- |
| 批次创建及授权者（团队 Owner/Admin 或 lead） | 创建批次；在「显式授权」为其他成员新增或撤销批次角色，不能自我授权；创建者不自动得到金额权限 |
| 金额负责人 | 创建时获得「方案编辑」「预算金额」「资格维护」角色；三者齐备才可保存、提交或修订人工方案；「方案编辑」与「预算金额」授权用于发布和记录模拟发放 |
| 独立核定人 | 获得「独立核定」角色，处理退回或独立核定，仍须通过利益冲突检查 |
| 审计人员 | 显式授予「审计查看」后查看金额工作区与历史，不因此获得编辑、核定或发放权 |
| 普通项目成员 / 受益人 | 可查看批次元数据；在「我的奖金」仅查看本人已核定且已发布的结果，不能查看他人金额 |

授权按批次生效，不从 ROOT、Owner/Admin 或 lead 自动继承金额权限。离队、项目成员变更与权限 epoch 会影响后续访问；仍须保持有效的团队与项目成员关系。

### 人工预算、核定与发布

1. 金额负责人进入「奖金方案工作区」，点击「编制人工方案」或「编辑人工方案」；从「添加已确认贡献来源」选择正式贡献确认，填写总预算、各来源预算及理由；
2. 对每位来源成员明确「具备奖金资格」、人工金额及「资格与金额理由」，无资格或零金额也要说明。页面以人民币元输入（最多两位小数），API/数据库使用整数 CNY 分；贡献比例仅作参考，**没有自动金额公式**。来源预算不可超过总预算，成员金额不可超过来源预算，余额单独保留；
3. 「保存人工方案」生成不可变草稿版本，不等于提交。核对后「提交独立核定」；核定人可「退回修改」，由负责人修改、保存再提交，或执行「独立核定」；
4. 核定后仍处于未发布状态，由具备发布授权的成员另行「发布正式结果」。成员才可在侧栏「我的奖金」看到本人正式结果；
5. 尚无发放记录时可「新建修订版本」；草稿和待审阶段不影响原结果，新版本独立核定后替换正式版本，另行发布后成员才可查看新结果。原历史记录不覆盖。任一模拟发放记录产生后，该批次不能再修订。

### 模拟发放与操作冲突

发布后，有权限的成员在「成员汇总与模拟发放」为正金额成员记录模拟发放，填写参考号、理由并确认。金额由后端按已发布结果生成，不可手工改写或重复记录；**这不是银行转账，也不证明现实中已付款**。

金额、资格、核定、发布与发放操作保留审计；后端执行团队隔离、权限 epoch 校验、乐观并发和请求幂等。出现版本冲突时先「刷新工作区」重新核对；网络异常导致结果未知时先查看历史，不要盲目重复操作。

## 10. 常见启动失败排查

| 现象 | 处理 |
| --- | --- |
| `docker: command not found` / Docker 未启动 | 启动 Docker Desktop；或提供 PostgreSQL，同时设置 `NEXORA_EXTERNAL_DATABASE=1` 与 `NEXORA_DATABASE_URL`（仍会迁移目标库） |
| 端口 3000 / 8080 被占用 | 核对所用环境文件中的 `NEXORA_WEB_PORT` / `NEXORA_API_PORT`，以及 `NEXORA_HTTP_ADDR` 端口是否一致；不要停止来源不明的服务 |
| API 提示 schema 不兼容 | 接受 v9–v11；v8 及更早版本须先备份、检查迁移状态并升级；v12+ 不得强行降级以绕过检查 |
| 奖金入口返回 404 | 确认已升级至 v11 并重启 API；v9/v10 不挂载奖金路由；再检查团队与项目成员资格 |
| 数据库连接失败 | 本地 Compose 检查 postgres 是否 healthy；外部模式核对目标连接与权限，不要求 Compose |
| ROOT 状态显示未知 | 检查 `/api/v1/meta` 和 `/readyz`；未知不等于未初始化，不要重复创建账号 |
| 登录后立即回到登录页 | 清除站点 Cookie 后重试；检查 API 的 `/readyz`，`/healthz` 不能证明数据库就绪 |
| 注册提示需要邀请 | 当前为 `invite` 模式；先由团队 Owner/Admin 邀请该用户名；全新安装先由平台管理员创建 Owner |
| 页面空白 / 控制台 401 | 匿名访问受保护接口属正常；若持续 401，重新登录 |
| 想重置或回退环境 | 先确认目标与同恢复点备份；v11 拒绝 Down，恢复到单独审核的目标库；不要删除未知数据库或数据卷 |

日志位置：`.run/api.log`、`.run/web.log`。

### 技术栈

Go + chi + pgx + goose；PostgreSQL 17；Vue 3 + TypeScript + Vite + Pinia + Vue Router + Tailwind CSS；OpenAPI 3.1 契约。

```text
apps/api/         Go 模块化单体（auth / teams / projects / tasks / submissions / contributions / bonusrounds / bonusresults）
apps/web/         Vue 工作台
infra/            容器、脚本、测试库与运维工具
docs/             产品、架构、API、开发与运维文档
```

### 常用命令

```bash

make build          # 后端与前端构建
```

本轮本地已通过全量 Go race/集成测试、前端 285 项测试及构建、37 项真实 Chrome E2E、空库交互启动与恢复演练；远程 CI 和发布状态以 [CHANGELOG 实际验证记录](CHANGELOG.md#实际验证记录2026-11-22) 为准，不以本地结果替代 Windows 或发布提交的 CI。

### 数据库与迁移

最终迁移链为 **v1–v11**，位于 `apps/api/internal/database/migrations/`。已发布的 **v1–v8 保持原始字节不变**；原未发布的奖金 v9 重编号为 v10，不改写已发布历史。

| Schema | 迁移 / 当前 API 能力 |
| --- | --- |
| v9 | `00009_task_progress_reports.sql`：Phase 07 进展上报；兼容 API，但不挂载奖金路由 |
| v10 | `00010_bonus_foundation.sql`：奖金基础结构；兼容 API，但仍不挂载奖金路由 |
| v11 | `00011_bonus_workflow.sql`：启用全部奖金读写、发布与模拟发放 |

API 启动与 `/readyz` 仅接受 **v9–v11**；v8 及更早版本必须先升级，v12+ 拒绝。正式启用 Alpha.2 全部功能应迁移至 v11 后重启 API。迁移需显式执行（`./start` 会自动 `up`）。如本地曾运行未发布的旧编号奖金迁移，应先核对真实 schema 和迁移记录，不要手改版本表或清库来绕过检查。

**v11 的 Down 明确拒绝，不支持一键回滚。** 升级前备份并验证数据库与附件的同一恢复点；需恢复时使用单独审核的目标库和私有附件目录，核对后再切换，不清理或覆盖未知数据。详见 [部署说明](docs/operations/deployment.md)。

生产使用独立 migration owner 与普通 app 账号，不把迁移凭据交给 API。迁移至 v11 后，先由 migration owner 按 [应用数据库角色](docs/operations/application-database-role.md)完成通用授权，再执行 `bonus_configure_application_role`；此后禁止批量 `GRANT EXECUTE ON ALL FUNCTIONS`，否则会重新开放奖金辅助函数。数据库 app 凭据属于可信后端；当前不是 RLS，不能声称抵抗数据库凭据完全泄露。

### 账号与会话安全

- 密码使用 Argon2id 哈希；
- 会话通过 HttpOnly Cookie 维持，不写入 localStorage；
- 变更请求需要 `X-Nexora-CSRF: 1`；
- 停用账号会立即撤销现有会话；
- 平台管理员与团队角色分离，团队权限始终由后端校验。
