## 1. 为什么不能直接把贡献比例乘以项目总奖金

Phase 05 的 10000 bps 是**单个已验收贡献案例内部**的人工份额；两项不同成果的 40% 和 60% 没有天然可比性。任务权重是进度权重，不是个人奖金价值；行数、提交次数、时长、负责人/作者角色也不是可靠的金额系数。

因此，未经新产品决策，禁止：
1. 将不同案例的 share_bps 简单相加作为成员的“项目贡献率”。
2. 用任务进度权重、代码提交量、工时或角色自动计算奖金。
3. 从最新草案、被推翻、未决争议或已失效确认读取奖金权重。
4. 将“结果已送达”视为“成员同意金额”。
5. 以内部奖金记录代替现实付款凭证。

## 2. 建议的 V2.0 最小纵向闭环（均待批准）

**建议方案 A：显式案例预算 → 案例内确认份额 → 人工复核分配。**

1. 创建与单个 Team / Project 关联的奖金计划；手工填写总预算、币种、用途、事前约定与授权依据。
2. 计划内逐项绑定**当前正式有效且不存在未决争议的**贡献确认（case version + confirmation + version digest）作为来源，并由授权人**明确填写每个案例分配预算**；禁止系统猜测跨案例价值。每个来源必须做出“纳入并给预算”或“明确排除并填理由”的覆盖决定，不允许遗漏。
3. 明确奖金资格，允许展示零贡献、无资格、未分配余额，但不静默重新分配排除项。任一绑定来源中的份额持有人若没有显式资格决定，计划不得提交核定。
4. 在每个案例内部，只有全部参与资格和业务政策满足时，才根据该案例既有 10000 bps **生成非权威的可解释建议**；授权人可人工调整并必须说明原因。
5. 所有建议金额、人工调整、未分配余额、资格快照和证明版本写入版本快照。审批前仅为草案；正式生效须另行独立确认。
6. 提交与核定两个时点都必须重新校验来源有效性、资格快照与金额合计；任一项变化即拒绝并要求新版本，禁止沿用旧金额。
7. 正式确认形成不可变版本；后续争议、更正、来源被推翻必须留痕并经新版本重审，不能原地改账。同一贡献确认不能被两个当前有效计划同时重复计入（具体政策见 D1/D9）。
8. 成员可查看本人的正式金额及来源；**已读/已收件与同意分配是不同事件**。是否需要明确同意、异议窗口和离队送达需产品批准。

**备选方案 B：项目级统一奖金权重。** 这需要额外批准可解释的**跨案例价值指数**及审核机制；Phase 05 明确未批准，本阶段不建议作为默认实现。

## 4. 候选不可变约束、金额模型与状态机（全部 Proposed）

**只允许精确整数或经批准的 NUMERIC，不用 JS/Go 浮点承载金钱。**

### 4.1 币种与金额精度

- 计划创建时冻结单一 `currency_code`（ISO 4217）与 `currency_minor_unit`；版本、来源、分配、核定必须与计划币种一致，禁止跨币种求和或隐含汇率。
- 金额字段一律为最小货币单位 `bigint`。USD 用分、JPY 用元、KWD 用三位小数；不得假设所有币种都有两位小数。
- 币种允许集、每币种最小单位与最大预算上限必须由产品批准；未列入允许集的币种直接拒绝。
- 为防止 `budget * 10000` 溢出 int64，计划总预算与任何来源预算必须满足 `amount <= 900_000_000_000_000`；数据库 CHECK 与服务层同时校验。金额汇总使用 SQL `numeric` 或受检整数加法，不以浮点求和。
- UI 只做显示换算，不参与计算；API 只接受整数最小单位，不接受字符串小数或科学计数法。

### 4.2 建议算法（仅案例内）

- 输入：该来源预算 `B`、该案例有效确认版本的 10000 bps 份额、资格决定、算法版本。
- 基础：`base_i = floor(B * bps_i / 10000)`；余数 `rem_i = (B * bps_i) mod 10000`。
- 余数：`L = B - Σ base_i`（0 ≤ L < 参与人数）按 `rem_i` 从大到小逐人加 1；余数相同时按 `user_id` 的 UUID 字节序升序打破平局。
- 可复现：算法版本与输入摘要写入版本快照；重算结果必须与快照完全一致；Go 与 PostgreSQL 的整数除法/取模语义必须一致。
- 无资格份额：**不得重算比例或静默重分**。默认将该份额对应金额留在显式“来源未分配”余额；只有授权人做出带理由的人工调整记录后，才能转给其他受益人。
- 案例内无任何合格受益人而预算大于 0 时，不得自动建议；必须显式转为未分配或经批准的调整。
- 任何代码路径都不得跨案例累加 `share_bps` 作为“项目贡献率”；跨案例只允许累加**金额**，且必须标注“逐案例建议之和”，不是贡献指数。

### 4.3 账务不变量（版本级）

- `total_budget_minor >= 0`；所有金额非负。
- `Σ source_budget_minor <= total_budget_minor`。
- `plan_unallocated_minor = total_budget_minor - Σ source_budget_minor`，必须显式存储，不得隐藏。
- 每个来源：`allocated_source_minor + source_unallocated_minor = source_budget_minor`。
- 计划级：`Σ final_minor + Σ source_unallocated_minor + plan_unallocated_minor = total_budget_minor`，精确相等。
- `suggested_minor` 与 `final_minor` 分离；两者不同时必须有人工调整记录、理由、操作者与请求 ID。
- 草案与待核定金额不得标记为正式；只有 confirmed 版本可被本人结果、历史查询与后续导出读取。
- 提交、核定在同一事务内锁定 Team → Plan → Source/Allocation，重算摘要并校验以上合计；任一失败全部回滚。

### 4.4 计划版本状态机与工作流

| 版本状态 | 语义 | 可编辑性 |
| --- | --- | --- |
| `draft` | 草案 | 来源、预算、资格、分配可编辑；金额非正式 |
| `pending_review` | 已提交待核定 | 内容冻结；合计、来源有效性与资格快照必须通过 |
| `confirmed` | 已核定 | 完全不可编辑；可成为有效版本 |
| `superseded` | 被更新确认版本取代 | 终态；确认事实保留 |
| `overturned` | 被正式裁定推翻 | 终态；确认事实保留 |
| `abandoned` | 草案被放弃 | 终态；无正式效力；必须审计 |

计划工作流状态由权威字段派生并由数据库校验，API 不可写；优先级：`disputed` > `revising` > `confirmed` > `pending_review` > `draft`。`cancelled` 只用于从未产生有效确认的计划；一旦存在 confirmed 版本，只能用 `superseded` / `overturned` 表达历史。

合法转换：

| 从 → 到 | 动作 | 条件 |
| --- | --- | --- |
| draft → pending_review | 提交 | 来源覆盖完整、资格决定完整、金额合计通过 |
| pending_review → draft | 撤回 | 提案人；未确认 |
| pending_review → confirmed | 核定 | 独立核定人；来源、资格与金额重验通过 |
| draft → abandoned | 放弃 | 必填理由 |
| confirmed → superseded | 新版本核定 | 仅在新核定的同一事务内 |
| confirmed → overturned | 裁定推翻 | 仅在推翻裁定同一事务内，并生成后继草案 |
| confirmed → disputed | 本人/代提异议 | 追加争议记录；不改金额、不清空指针 |
| disputed → confirmed | 裁定维持 | 追加裁定；金额与有效指针不变 |
| disputed → revising | 裁定推翻 | 清空有效指针、版本 overturned、生成新草案 |

版本指针与不可变事实：

- `latest_version_id` 只用于工作流，单调递增；`effective_confirmed_version_id` 是正式金额的唯一读取入口。
- 每个版本至多一条不可变确认记录；确认摘要覆盖总预算、币种/最小单位、来源（含份额快照与预算）、资格快照、建议金额、最终金额、算法版本与调整记录。
- 确认、争议裁定、来源快照、调整记录均只追加；禁止 UPDATE/DELETE 历史。
- 旧有效版本只在新确认事务内变 `superseded`；`overturned` 必须清空有效指针并生成后继草案，不能原地改账。
- 归档项目当前只读。奖金计划的创建/修改与归档先后关系需单独批准，不能绕过现有 Phase 05 归档不变量；任何奖金写入都不得绕过 `contribution_archive_guard` 对正式验收与收件证据的要求。

## 5. 候选权限矩阵（未批准，不得实现为正式授权）

前置：Team Owner / Team Admin / Project Lead / ROOT 身份**本身不产生任何奖金权限**；所有奖金操作必须由显式授权产生，并按成员 epoch 失效。

| 动作 | 建议候选 | 关键约束 |
| --- | --- | --- |
| 创建/编辑草案、绑定来源 | 显式授权的奖金管理人 | 有效 Team/Project 范围；epoch 绑定；完整审计 |
| 设定总预算与来源预算 | 显式授权的预算管理人 | 可与编辑人为同一人，但审计中必须区分动作 |
| 提出资格建议 | 奖金管理人 | 不得决定自己的资格 |
| 批准/否决资格 | 独立资格审核人 | 不得审核本人；变更需理由与 epoch 快照 |
| 人工调整金额 | 奖金管理人 | 记录前后值、理由；受益人可提案但不得最终决定自己的调整 |
| 正式核定 | 独立核定人 | 非计划创建人、非任何调整人、非受益人、非来源贡献核定人；无合格人则保持待核定 |
| 查看本人正式金额 | 本人 | 仅本人；不泄露他人金额或整包预算 |
| 查看计划整体/历史 | 显式授权的审核人 | 不以贡献可读权限自动等同奖金可读 |
| 提出异议/收件 | 本人 / 经验证代提 | 收件 ≠ 认可；离队成员需独立安全方案 |
| ROOT 平台支持 | 只读且显式审计，或不允许 | 不得因 ROOT 自动获得写权限或绕过业务授权 |

职责分离（建议默认）：

- 核定人 ≠ 计划创建人；核定人 ≠ 任何人工调整的作出人；核定人不得是任何受益人；核定人不得是任一绑定来源的贡献提案人或贡献核定人。
- 资格审核人不得批准自己的资格；受益人不得最终决定自己的调整。
- 若找不到满足条件的核定人，计划必须停留在 `pending_review`；系统不得自动指派、自动降级或由 ROOT 兜底。
- 授权被撤销、成员离队或重新加入导致 epoch 变化时，旧授权立即失效；核定事务必须重验授权与 epoch。
- 同一自然人不得通过多个角色组合绕开上述限制；数据库约束与服务层必须同时执行，不接受仅前端隐藏按钮。

任何涉及财务角色、例外授权、单人团队审批或离队资格的具体政策，都必须由产品负责人批准。

## 6. 核心验收场景（后续 M2–M6 应覆盖）

1. 金额为 0、1 最小单位、大值、多人分摊与余数并列；整数溢出/错误币种全部拒绝。
2. 贡献案例有争议、被推翻、被替代、只是草案、来源审查不合法时不产生权威金额。
3. 没资格者、历史成员、零贡献者、预算未分配、超预算方案处理明确且不静默重分。
4. 跨 Team/Project IDOR、ROOT 非业务授权、核定人受益/提案/调整冲突、已撤销授权。
5. 同一请求 ID 重放、不同 ID 重试、并发核定、旧 expected_version、重复确认和回滚原子性。
6. 正式确认前后版本差异、不可变历史、未决异议与源贡献修订的传播规则。
7. 数据库约束（非仅前端提示）、最小应用角色、审计不可删改、真实 PostgreSQL -race 集成与 E2E。
8. 已读与同意隔离；无可信本人送达不伪装成完成；脱离项目后可见性依批准政策实现。
9. 同一贡献确认被两个有效计划重复引用、计划总预算小于来源预算合计、来源被排除但未填理由。
10. 来源确认在提交/核定之间被 superseded、overturned 或新增未决争议；资格 epoch 变化；旧快照必须被拒绝。
11. 归档项目创建/修改奖金计划；归档后来源失效；不得放宽 Phase 05 归档门禁。
12. 收件复用历史告知、摘要不匹配、离队成员无送达渠道；不得把收件当同意或伪造完成。

| A2 | 来源覆盖 | 项目全部有效确认案例必须“纳入”或“明确排除并填理由”，不允许遗漏。 |
| A3 | 极小团队/无独立核定人 | 保持待核定，不设自动例外、不自动降级给 Team Owner 或 ROOT。 |
| A4 | ROOT/平台支持访问 | 无写权限；只读支持需显式审计授权。 |
| A5 | 归档级收件 | 是否要求核定后逐人收件才允许归档或导出；未批准前不得声称完成送达。 |

审批必须是明确的产品决策记录，不能把“讨论了设计”视为批准。

## 8. 建议实施分期（M1 通过后再进入）

- **M1（当前）**：PRD 对齐、方案比较、权限/幂等/金额不变量、D1–D10 与 A1–A5 产品审批；本轮已完成独立设计评审，但仍为 Proposed。
- **M2**：只在审批后设计/实施追加 Schema v8、迁移与数据库完整性回归；保留 00001–00007 原样。
- **M3**：受限数据库角色、Go Service/Repository、认证 API 和 OpenAPI；锁、冲突与审计完备。
- **M4**：Vue 奖金草案、来源证据、人工调整、核定与本人结果界面；不显示任何未批准的正式金额。
- **M5**：舍入、权限、并发、幂等、争议与性能加固。
- **M6**：真实多角色 E2E、恢复与安全验收及发布候选评估。

**M2 进入条件（全部满足）：**

1. D1–D10 与 A1–A5 有明确产品批准记录；
2. 评审报告中的 P1 项全部关闭或转为已批准决策；
3. Schema v8 设计评审通过，明确只追加、不改 00001–00007；
4. 金额算法、币种允许集、上限、舍入与破平局规则冻结；
5. 权限矩阵与职责分离经产品确认；
6. 归档项目奖金策略与离队送达策略有结论（可明确为“暂不支持”）。

所有工作走 feature → PR → develop；历史迁移不可改，`main` 不因阶段通过而自动发布。Alpha/MVP 运行配置由产品负责人另行管理，不在本设计交付范围。

## 9. 当前交付结论

本 M1 文件只建议一个**可解释、不能自动猜跨成果价值、可审计**的奖金计划模型。**Phase 06 尚未实现，也未批准任何自动奖金分配算法**。本轮独立设计评审已完成，D1–D10 与 A1–A5 全部保持 Proposed；下一门禁是产品负责人的正式批准。未获批准前不得执行 M2 金额表迁移、开发金额业务 API，或把任何草案金额当作正式结果。
