## 1. 为什么不能直接把贡献比例乘以项目总奖金

Phase 05 的 10000 bps 是**单个已验收贡献案例内部**的人工份额；两项不同成果的 40% 和 60% 没有天然可比性。任务权重是进度权重，不是个人奖金价值；行数、提交次数、时长、负责人/作者角色也不是可靠的金额系数。

因此，未经新产品决策，禁止：
1. 将不同案例的 share_bps 简单相加作为成员的“项目贡献率”。
2. 用任务进度权重、代码提交量、工时或角色自动计算奖金。
3. 从最新草案、被推翻、未决争议或已失效确认读取奖金权重。
4. 将“结果已送达”视为“成员同意金额”。
5. 以内部奖金记录代替现实付款凭证。

## 2. 建议的 V2.0 最小纵向闭环（均待批准）

**建议方案 A：显式案例预算 → 案例内确认份额 → 人工复核分配。**

1. 创建与单个 Team / Project 关联的奖金计划；手工填写总预算、币种、用途、事前约定与授权依据。
2. 计划内逐项绑定**当前正式有效且不存在未决争议的**贡献确认（case version + confirmation + digest）作为来源，并由授权人**明确填写每个案例分配预算**；禁止系统猜测跨案例价值。
3. 明确奖金资格，允许展示零贡献、无资格、未分配余额，但不静默重新分配排除项。
4. 在每个案例内部，只有全部参与资格和业务政策满足时，才根据该案例既有 10000 bps **生成非权威的可解释建议**；授权人可人工调整并必须说明原因。
5. 所有建议金额、人工调整、未分配余额和证明版本写入版本快照。审批前仅为草案；正式生效须另行独立确认。
6. 正式确认形成不可变版本；后续争议、更正、来源被推翻必须留痕并经新版本重审，不能原地改账。
7. 成员可查看本人的正式金额及来源；**已读/已收件与同意分配是不同事件**。是否需要明确同意、异议窗口和离队送达需产品批准。

**备选方案 B：项目级统一奖金权重。** 这需要额外批准可解释的**跨案例价值指数**及审核机制；Phase 05 明确未批准，本阶段不建议作为默认实现。

## 4. 候选不可变约束和金额算术

**只允许精确整数或经批准的 NUMERIC，不用 JS/Go 浮点承载金钱。**

- 计划固定单一币种。最小货币单位的比例依币种而定，不可假设所有币种均有“两位小数”。币种允许集与舍入规则须批准。
- 每个版本满足：总预算 >= 0；来源预算、已分配金额、未分配余额均非负；来源预算合计 <= 总预算；成员最终金额合计 + 未分配余额 = 总预算（具体是否保留专项余额待批准）。
- 建议算法候选：对**单一案例已获批准预算**，按该案例确认的 10000 bps 比例使用整数除法得到基础金额，余数按“最大余数法”处理；相同余数用稳定的成员 UUID 顺序打破平局，产生完全可重现的结果。
- 若部分份额持有人无奖金资格，**不能**悄悄把其金额按剩余者比例重分。默认应阻止自动建议并要求人工决策/显式保留余额（精确政策待批准）。
- 输入必须固定对应的当前有效确认，明确记录核定来源与摘要。旧确认被 superseded / overturned 后，不能自动将其继续视为新的有效依据；历史方案留痕、当前生效状态如何变化需先定政策。
- 提交/核定使用 expected_version、client_request_id、事务锁、幂等重放；同一计划版本不可并发双重确认。权限最终由服务端与数据库约束执行。
- 归档项目当前只读。奖金计划的创建/修改与归档先后关系需单独批准，不能绕过现有 Phase 05 归档不变量。

## 5. 候选权限矩阵（未批准，不得实现为正式授权）

| 动作 | 建议候选 | 约束 |
| --- | --- | --- |
| 创建/编辑草案 | 明确授权的项目奖金管理人 | 必须是有效 Team/Project 范围；完整审计 |
| 填写奖金资格/人工调整 | 具备显式资金分配授权的人 | 不能因 ROOT 或 Team 管理员身份自动获取 |
| 正式核定 | 与调整、受益关系独立的核定人 | COI 与授权撤销必须在提交事务中重验 |
| 查看本人正式金额 | 实际且获授权的本人 | 仅本人，不泄露 Team 其他人预算或明细 |
| 查看计划整体/历史 | 显式授权的审核人 | 不可将既有贡献可读权限自动等同奖金可读 |
| 提出异议与确认收件 | 本人 / 经验证代提渠道 | 收件 ≠ 认可；离队成员需独立安全方案 |

任何涉及财务角色、例外授权、单人团队审批或离队资格的具体政策，都必须由产品负责人批准。

## 6. 核心验收场景（后续 M2–M6 应覆盖）

1. 金额为 0、1 最小单位、大值、多人分摊与余数并列；整数溢出/错误币种全部拒绝。
2. 贡献案例有争议、被推翻、被替代、只是草案、来源审查不合法时不产生权威金额。
3. 没资格者、历史成员、零贡献者、预算未分配、超预算方案处理明确且不静默重分。
4. 跨 Team/Project IDOR、ROOT 非业务授权、核定人受益/提案/调整冲突、已撤销授权。
5. 同一请求 ID 重放、不同 ID 重试、并发核定、旧 expected_version、重复确认和回滚原子性。
6. 正式确认前后版本差异、不可变历史、未决异议与源贡献修订的传播规则。
7. 数据库约束（非仅前端提示）、最小应用角色、审计不可删改、真实 PostgreSQL -race 集成与 E2E。
8. 已读与同意隔离；无可信本人送达不伪装成完成；脱离项目后可见性依批准政策实现。

## 7. 需要产品负责人批准的 10 个决定

| ID | 待决策项 | 本文建议（仅 Proposed） |
| --- | --- | --- |
| D1 | 计划作用域 | 每 Team + Project 一套或多套独立计划，严格不跨租户 |
| D2 | 跨成果预算权重 | 方案 A：每案例预算由授权人显式填写；不设计综合指数 |
| D3 | 奖金资格 | 独立的人工授权资格，不能仅据 Team/Project 成员身份 |
| D4 | 无资格份额 | 阻止自动建议，人工处理或作为显式未分配余额 |
| D5 | 币种与金额精度 | 单计划单币种，最小单位整数，明确币种小数位政策 |
| D6 | 舍入及余款 | 案例内最大余数法；总池未分配额单独展示 |
| D7 | 核定权限与回避 | 独立核定、实时重验 COI，不默认 ROOT/管理员兜底 |
| D8 | 申诉/成员确认 | 收件与认可分离，明确拒绝、时限和补正权限 |
| D9 | 归档及贡献失效 | 明确奖金冻结、原确认被推翻后的补救及审计 |

## 8. 建议实施分期（M1 通过后再进入）

- **M1（当前）**：PRD 对齐、方案比较、权限/幂等/金额不变量、D1–D10 产品审批。
- **M2**：只在审批后设计/实施追加 Schema v8、迁移与数据库完整性回归；保留 00001–00007 原样。
- **M3**：受限数据库角色、Go Service/Repository、认证 API 和 OpenAPI；锁、冲突与审计完备。
- **M4**：Vue 奖金草案、来源证据、人工调整、核定与本人结果界面；不显示任何未批准的正式金额。
- **M5**：舍入、权限、并发、幂等、争议与性能加固。
- **M6**：真实多角色 E2E、恢复与安全验收及发布候选评估。

所有工作走 feature → PR → develop；历史迁移不可改，\`main\` 不因阶段通过而自动发布。Alpha/MVP 运行配置由产品负责人另行管理，不在本设计交付范围。

## 9. 当前交付结论

本 M1 文件只建议一个**可解释、不能自动猜跨成果价值、可审计**的奖金计划模型。**Phase 06 尚未实现，也未批准任何自动奖金分配算法**。下一门禁是 D1–D10 的正式审查与授权；未获批准前不得执行 M2 金额表迁移或开发金额业务 API。
