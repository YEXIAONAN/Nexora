## 1. 为什么不能直接把贡献比例乘以项目总奖金

Phase 05 的 10000 bps 是**单个已验收贡献案例内部**的人工份额；两项不同成果的 40% 和 60% 没有天然可比性。任务权重是进度权重，不是个人奖金价值；行数、提交次数、时长、负责人/作者角色也不是可靠的金额系数。

因此，未经新产品决策，禁止：
1. 将不同案例的 share_bps 简单相加作为成员的“项目贡献率”。
2. 用任务进度权重、代码提交量、工时或角色自动计算奖金。
3. 从最新草案、被推翻、未决争议或已失效确认读取奖金权重。
4. 将“结果已送达”视为“成员同意金额”。
5. 以内部奖金记录代替现实付款凭证。

## 2. 建议的 V2.0 最小纵向闭环（均待批准）

**建议方案 A：显式案例预算 → 案例内确认份额 → 人工复核分配。**

1. 创建与单个 Team / Project 关联的奖金计划；手工填写总预算、币种、用途、事前约定与授权依据。
2. 计划内逐项绑定**当前正式有效且不存在未决争议的**贡献确认（case version + confirmation + version digest）作为来源，并由授权人**明确填写每个案例分配预算**；禁止系统猜测跨案例价值。每个来源必须做出“纳入并给预算”或“明确排除并填理由”的覆盖决定，不允许遗漏。
3. 明确奖金资格，允许展示零贡献、无资格、未分配余额，但不静默重新分配排除项。任一绑定来源中的份额持有人若没有显式资格决定，计划不得提交核定。
4. 在每个案例内部，只有全部参与资格和业务政策满足时，才根据该案例既有 10000 bps **生成非权威的可解释建议**；授权人可人工调整并必须说明原因。
5. 所有建议金额、人工调整、未分配余额、资格快照和证明版本写入版本快照。审批前仅为草案；正式生效须另行独立确认。
6. 提交与核定两个时点都必须重新校验来源有效性、资格快照与金额合计；任一项变化即拒绝并要求新版本，禁止沿用旧金额。
7. 正式确认形成不可变版本；后续争议、更正、来源被推翻必须留痕并经新版本重审，不能原地改账。同一贡献确认不能被两个当前有效计划同时重复计入（具体政策见 D1/D9）。
8. 成员可查看本人的正式金额及来源；**已读/已收件与同意分配是不同事件**。是否需要明确同意、异议窗口和离队送达需产品批准。

**备选方案 B：项目级统一奖金权重。** 这需要额外批准可解释的**跨案例价值指数**及审核机制；Phase 05 明确未批准，本阶段不建议作为默认实现。

## 4. 候选不可变约束、金额模型与状态机（全部 Proposed）

**只允许精确整数或经批准的 NUMERIC，不用 JS/Go 浮点承载金钱。**

### 4.1 币种与金额精度

- 计划创建时冻结单一 `currency_code`（ISO 4217）与 `currency_minor_unit`；版本、来源、分配、核定必须与计划币种一致，禁止跨币种求和或隐含汇率。
- 金额字段一律为最小货币单位 `bigint`。USD 用分、JPY 用元、KWD 用三位小数；不得假设所有币种都有两位小数。
- 币种允许集、每币种最小单位与最大预算上限必须由产品批准；未列入允许集的币种直接拒绝。
- 为防止 `budget * 10000` 溢出 int64，计划总预算与任何来源预算必须满足 `amount <= 900_000_000_000_000`；数据库 CHECK 与服务层同时校验。金额汇总使用 SQL `numeric` 或受检整数加法，不以浮点求和。
- UI 只做显示换算，不参与计算；API 只接受整数最小单位，不接受字符串小数或科学计数法。

### 4.2 建议算法（仅案例内；全部仍为 Proposed）

按下面**不可交换的步骤**计算；资格过滤绝不能放在最大余数法之前：

1. 固定有效确认的**全部**份额持有人（含无资格及历史成员）及其原始 `share_bps`，必须合计 10000。输入该来源预算 `B`、确认摘要、资格快照、算法版本。
2. 对全部持有人计算 `base_i = floor(B * bps_i / 10000)`、`rem_i = (B * bps_i) mod 10000`。余下 `L = B - Σbase_i` 单位按余数从高到低发放；余数相同按 `user_id` UUID 字节序升序。得到 `raw_rounded_minor_i`，必须 `Σraw_rounded_minor_i = B`。
3. **然后**读取资格：合格者的 `eligible_suggested_minor_i = raw_rounded_minor_i`；无资格者的建议与最终金额默认都是 0，属于其 `raw_rounded_minor_i` 的金额进入该来源 `source_unallocated_minor`。资格决定缺失则整个草案不可提交，不允许用“未决定”代替“无资格”。
4. 只允许**带来源 ID 的**人工调整：在同一来源中减少/增加受益人的 `final_minor`，或经授权把该来源的未分配余额转给有资格成员；逐笔保存前后值、原因、操作者和请求 ID。任何修改都要保持来源总额等式。不得通过成员层汇总反向分配，也不得静默挪用另一个来源的预算；跨来源预算变化必须修改有审计的新草案/版本并重新核算。
5. 保存上述全部原始舍入行、资格分流、调整、算法版本及输入摘要，保证 Go 与 PostgreSQL 重算一致。**一个成员跨案例的总金额只是来源明细求和的只读投影，不是项目贡献率，也不是独立可写记录。**

**1 最小单位反例（强制回归）**：两个持有人各 5000 bps，预算仅 1 单位；较小 UUID 为**无资格**成员。步骤 2 的唯一 1 单位必须先归较小 UUID 的原始舍入份额，随后进入 `source_unallocated_minor=1`；另一位合格成员建议金额仍为 **0**。若先过滤无资格者、把 1 单位给合格者，即属于错误重分。

案例内全部无资格时，仍保留全部原始舍入与明确的来源未分配余额；是否允许正式核定含未分配余额，须由 D4/D6 批准。

### 4.3 逐来源账务不变量（版本级；全部仍为 Proposed）

- 金额使用最小货币单位整数且非负；`Σ source_budget_minor <= total_budget_minor`。`plan_unallocated_minor = total_budget_minor - Σ source_budget_minor`，明确保存，不隐藏。
- 对每个**已纳入**的来源 `s`：`Σ final_minor(s, user) + source_unallocated_minor(s) = source_budget_minor(s)`；被明确排除的来源不得有非零预算或分配行。
- 整个计划：`Σ_all_sources_and_users final_minor + Σ_all_sources source_unallocated_minor + plan_unallocated_minor = total_budget_minor`，精确相等。每位成员的 `member_total_minor = Σ_sources final_minor(s, member)` 为只读聚合，不允许独立写入。
- **权威键必须包含来源**：`BonusAllocationLine(plan_version_id, source_id, user_id)` 唯一；`BonusAdjustment` 必须绑定同一 `source_id` 及成员，并追加式记录 `old/new/delta`、原因、操作者、请求 ID、变化时的未分配余额。调整不自动改变其他来源预算；需要跨来源转移时，先显式改来源预算并生成经审计的新草案/版本。
- 无资格者的 `final_minor` 必须为 0；只有新的显式资格决定/计划版本才能改变资格，不能以“调整原因”绕过资格检查。最终金额不同于该来源合格建议金额时必须有来源级调整记录。
- `raw_rounded_minor` 对所有持有人先算并合计来源预算；资格分流后，`Σ eligible_suggested + initial_source_unallocated = B`。禁止过滤无资格成员后重新分配最大余数。
- 草案与待核定金额均非正式；本人正式结果仅从有效 confirmed 版本逐来源明细派生。
- 提交与核定在同一事务内锁定 Team → Plan → Source/Allocation，重新校验来源有效性、资格快照、摘要和**每来源及计划两层**精确守恒；任何失败全部回滚。

**跨来源重叠成员举例（仅验证设计守恒）**：来源 A、B 各预算 1000 最小单位。A 的甲/乙原建议 600/400，B 的甲/乙建议 300/700。若 A 由授权人记录甲 -10、乙 +10 的**两条来源级调整**，A 变为 590/410，B 仍 300/700；A、B 均各合计 1000，计划合计 2000，甲的只读汇总为 890，乙为 1110。若只将甲汇总改为 890 而缺少 A 的调整与对应乙的变更，必须拒绝。

### 4.4 **版本状态机**与**计划工作流状态**必须独立（全部 Proposed）

**版本状态是不可变事实的生命周期**，只有被授权的受控状态转换可以改变版本元数据；版本内容在离开 draft 后永久冻结：

| 版本状态 | 语义 | 内容可编辑性 |
| --- | --- | --- |
| `draft` | 可编辑草案 | 仅此状态可编辑来源、资格快照、分配行 |
| `pending_review` | 已提交、等待独立核定 | 内容冻结，不允许重新编辑同一版本 |
| `confirmed` | 已正式确认 | 内容与确认记录永久不可变 |
| `superseded` | 后继确认在同一事务内替代旧版本 | 原确认历史完整保留 |
| `overturned` | 由独立裁定推翻 | 原确认历史完整保留 |
| `abandoned` | 草案或待审版本被放弃/撤回 | 内容不可重开编辑，必须审计 |

**合法的版本级转换（只允许以下边，状态变化须受限数据库触发器授权）**：

| 原版本 → 新版本状态 | 原因 | 必须的原子性 |
| --- | --- | --- |
| `draft → pending_review` | 提交 | 来源/资格覆盖与两层守恒校验、冻结摘要 |
| `draft → abandoned` | 放弃 | 记录原因，必要时另建新 draft |
| `pending_review → abandoned` | 撤回待核定申请 | 原版本不返回 draft；如需改动，**创建递增版本的新 draft** |
| `pending_review → confirmed` | 独立核定 | 最新版本、有效授权、来源未失效、无利益冲突、唯一确认 |
| `confirmed → superseded` | 后继版本获确认 | 同一事务生成新确认、更新有效指针 |
| `confirmed → overturned` | 独立裁定推翻 | 同一事务清空有效指针、追加裁定及后继 draft |

**计划工作流**只可由 `latest_version_id`、`effective_confirmed_version_id`、未决争议以及显式取消事件**派生**，API 不接收任意状态更新：

| 事件 / 条件 | 派生计划工作流 | 有效版本与历史 |
| --- | --- | --- |
| 只有最新 draft、无有效确认 | `draft` | 正式金额为空 |
| 只有最新 pending_review、无有效确认 | `pending_review` | 正式金额为空 |
| 有有效 confirmed、无未决争议与后继草案 | `confirmed` | 只读该有效版本 |
| 有有效 confirmed，出现未决争议 | `disputed` | **原版本仍为 confirmed**，确认与金额不变；页面标记争议中，禁止将其作为无争议新来源 |
| 有有效 confirmed，另有更新的 draft/pending_review | `revising` | 有效旧版仍可追溯，新草案非正式 |
| 裁定推翻有效确认且新 draft 已生成 | `revising` | 有效指针为空，旧版本为 overturned |
| 争议裁定维持、无更新草案 | `confirmed` | 旧版确认未改变 |
| 无有效版本且所有草案均被放弃 | `abandoned` | 无正式金额 |
| 从未有确认，存在已批准的明确取消事件 | `cancelled` | 只记录终止事实，不复写历史 |

如多条件同时成立，必须明确确定性优先级（建议 `disputed > revising > confirmed > pending_review > draft > abandoned`），但版本状态永不变成 `disputed` 或 `revising`。尤其**“收到异议”不是 `confirmed → disputed` 的版本状态转换**。

- `latest_version_id` 指向本计划单调递增的最新版本；`effective_confirmed_version_id` 只能指向本计划有效且已核定的 confirmed 版本，是正式金额唯一入口。
- 确认摘要覆盖计划/币种、全部来源与份额快照、逐来源分配行、资格分流、未分配额、调整与算法版本；每版本至多一个不可变确认。
- 旧有效版本仅在新确认的同一事务内变 `superseded`；推翻须有独立裁定并清空有效指针/生成新草案，不得修改旧金额。
- 归档项目仍只读；奖金域归档前后政策待 D9 批准，任何奖金写入不得弱化 Phase 05 的 `contribution_archive_guard`。

## 5. 候选权限矩阵（未批准，不得实现为正式授权）

前置：Team Owner / Team Admin / Project Lead / ROOT 身份**本身不产生任何奖金权限**；所有奖金操作必须由显式授权产生。内部审核授权按成员 epoch 失效；**若 D7/A3 批准外部独立核定**，只能使用经身份核验、限定单计划与证据范围、可撤销且有期限的独立授权版本，不能依靠不存在的 Project 成员 epoch，也不能自动获得 Team/Project 通用读取权限。

| 动作 | 建议候选 | 关键约束 |
| --- | --- | --- |
| 创建/编辑草案、绑定来源 | 显式授权的奖金管理人 | 有效 Team/Project 范围；epoch 绑定；完整审计 |
| 设定总预算与来源预算 | 显式授权的预算管理人 | 可与编辑人为同一人，但审计中必须区分动作 |
| 提出资格建议 | 奖金管理人 | 不得决定自己的资格 |
| 批准/否决资格 | 独立资格审核人 | 不得审核本人；变更需理由与 epoch 快照 |
| 人工调整金额 | 奖金管理人 | 记录前后值、理由；受益人可提案但不得最终决定自己的调整 |
| 正式核定 | 内部独立核定人；或**经 D7/A3 批准后**的外部独立核定人 | 同一套利益冲突排除；外部授权必须仅限单计划核定所需的最小证据与权限；无合法候选人则保持待核定 |
| 查看本人正式金额 | 本人 | 仅本人；不泄露他人金额或整包预算 |
| 查看计划整体/历史 | 显式授权的审核人 | 不以贡献可读权限自动等同奖金可读 |
| 提出异议/收件 | 本人 / 经验证代提 | 收件 ≠ 认可；离队成员需独立安全方案 |
| 外部独立核定授权（待批准） | 明确授权的独立自然人，不要求一般 Project 成员资格 | 核实身份、无利益关系、单计划权限、限时、可撤销、全程审计；不得跨 Team 横向读取 |
| ROOT 平台支持 | 只读且显式审计，或不允许 | 不得因 ROOT 自动获得写权限或绕过业务授权 |

职责分离（建议默认）：

- 核定人 ≠ 计划创建人；核定人 ≠ 任何人工调整的作出人；核定人不得是任何受益人；核定人不得是任一绑定来源的贡献提案人或贡献核定人。
- 资格审核人不得批准自己的资格；受益人不得最终决定自己的调整。
- 内部候选人必须为有效 Team/Project 成员且持有当前 epoch 的奖金核定授权；外部候选人只能在 D7/A3 **明确批准后**通过计划级限时授权参与，并受到**同等**回避谓词约束。全部成员均受益时，不能让任一受益人组成“多人会签”来消除利益冲突。
- 若没有符合政策的内部/获批准外部核定人，计划必须保持 `pending_review`；不得自动指派、开放全 Team 可读、将 ROOT 当例外，或暗中降低回避要求。
- 授权被撤销、成员离队或重新加入导致 epoch 变化时，旧授权立即失效；核定事务必须重验授权与 epoch。
- 同一自然人不得通过多个角色组合绕开上述限制；数据库约束与服务层必须同时执行，不接受仅前端隐藏按钮。

任何涉及财务角色、例外授权、单人团队审批或离队资格的具体政策，都必须由产品负责人批准。

## 6. 核心验收场景（后续 M2–M6 应覆盖）

1. 金额为 0、1 最小单位、大值、多人分摊与余数并列；整数溢出/错误币种全部拒绝。
2. 贡献案例有争议、被推翻、被替代、只是草案、来源审查不合法时不产生权威金额。
3. 没资格者、历史成员、零贡献者、预算未分配、超预算方案处理明确且不静默重分。
4. 跨 Team/Project IDOR、ROOT 非业务授权、核定人受益/提案/调整冲突、已撤销授权。
5. 同一请求 ID 重放、不同 ID 重试、并发核定、旧 expected_version、重复确认和回滚原子性。
6. 正式确认前后版本差异、不可变历史、未决异议与源贡献修订的传播规则。
7. 数据库约束（非仅前端提示）、最小应用角色、审计不可删改、真实 PostgreSQL -race 集成与 E2E。
8. 已读与同意隔离；无可信本人送达不伪装成完成；脱离项目后可见性依批准政策实现。
9. 同一贡献确认被两个有效计划重复引用、计划总预算小于来源预算合计、来源被排除但未填理由。
10. 来源确认在提交/核定之间被 superseded、overturned 或新增未决争议；资格 epoch 变化；旧快照必须被拒绝。
11. 归档项目创建/修改奖金计划；归档后来源失效；不得放宽 Phase 05 归档门禁。
12. 收件复用历史告知、摘要不匹配、离队成员无送达渠道；不得把收件当同意或伪造完成。
13. 同一成员存在于 A/B 两来源，只更改 A 的分配；B 不变且 A/B 各自守恒，成员汇总只读派生；缺少 source_id 的人工调整被拒绝。
14. 全团队都是受益人：内部独立核定候选为零，必须保持 pending_review；只有经批准、已验证身份且范围受限的外部审计授权才能核定，撤销/超期立即失效。
15. 已确认版本产生未决异议：只改变计划派生工作流，不改变版本 status 或确认内容；撤回 pending_review 必须留下 abandoned 旧版并新建递增 draft。
16. 预算为 1 最小单位、两个持有人各 5000 bps、较小 UUID 无资格：原始舍入 1 单位归该人再进入来源未分配，合格人得 0；先过滤再舍入的实现必须失败。

## 9. 当前交付结论

本 M1 文件只建议一个**可解释、逐来源守恒、不能自动猜跨成果价值、可审计**的奖金计划模型。补充评审已将逐来源/逐成员分配行、状态机轴分离、资格舍入顺序及外部独立核定候选方案写入设计；四项均为设计整改，**未获得 D1–D10 / A1–A5 批准**。**Phase 06 尚未实现，也未批准任何自动奖金分配算法**。本轮独立设计评审已完成，D1–D10 与 A1–A5 全部保持 Proposed；下一门禁是产品负责人的正式批准。未获批准前不得执行 M2 金额表迁移、开发金额业务 API，或把任何草案金额当作正式结果。
