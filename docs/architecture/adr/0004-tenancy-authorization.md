# ADR 0004：团队隔离与授权模型

- 状态：已接受（Accepted）
- 原提议日期：2026-10-29
- 批准日期：2026-11-17
- 批准依据：产品负责人于 2026-11-17 正式选择方案 B（多 Team 数据与权限架构先行，首版优先交付 ZERO_R 核心业务闭环），V1.0 PRD 同步生效。

## 背景

平台单实例承载多个团队。仅靠前端隐藏按钮或全局角色无法防止 IDOR（越权访问对象）。

## 决策（2026-10-29 原提议，保留）

1. 所有团队业务表包含 `team_id NOT NULL` 与外键。
2. 授权在 Service 层执行，顺序为：身份 → 团队归属 → 团队角色 → 项目角色 → 操作 → 资源状态。
3. Repository 查询必须带 `team_id`，禁止先按 ID 读取再内存判断。
4. 跨团队访问返回 404，避免泄漏存在性。
5. 平台角色与团队角色分离；ROOT 使用不可变 `system_root` 标记，不以用户名判断。
6. 所有授权失败写入安全审计（不含敏感载荷）。
7. 每个阶段补充跨团队越权集成测试。

## 后果（原提议，保留）

- 查询签名普遍需要 `teamID` 参数。
- 需要在 CI 中维护越权测试矩阵。
- 批量与导出接口必须逐项校验。

## 实施细则（2026-11-17 新增，随方案 B 批准）

> 本节是方案 B 落地时新增的实施规则与业务规则，明确标注为新增内容，不是 2026-10-29 的历史决策。与原决策冲突之处以本节为准；未发现重大安全或业务冲突。

### 用户与团队关系

- 一个 User 可以关联多个 Team；`team_members` 维护多对多关系：`team_id`、`user_id`、`role`、`status`（active/removed）、`created_at`、`updated_at`、`removed_at`。
- `(team_id, user_id)` 为主键（唯一约束），重复成员关系由数据库防护。
- 团队角色：`owner`、`admin`、`member`。用户在 Team A 为 owner，不意味着在 Team B 具有任何权限；角色只在所属 Team 内生效。
- 移除成员使用软删除（`status='removed'` + `removed_at`），保留历史；重新邀请可恢复同一行。
- 成员移除后权限即时失效：授权每次请求实时查询成员关系，不在会话中缓存团队权限；被移除成员的其他 Team 访问不受影响。

### 资源所属与跨 Team 完整性

- 所有团队业务资源必须明确关联 Team；团队资源查询必须包含 tenant/team 约束。
- `team_members` 主键 `(team_id, user_id)` 同时作为未来跨表业务关联的复合外键目标（如项目成员表引用 `(team_id, user_id)`），从数据库层避免跨 Team 错误挂接。
- 邀请表同时引用 `team_id` 与 `invited_user_id`；接受邀请时成员关系只能写入邀请所属 Team，不接受客户端另行指定 Team。

### 授权链与职责分层

```text
认证身份（会话 Cookie → 服务端会话记录）
  → 确定资源所属 Team（URL 路径解析，且与数据库记录一致）
  → 验证成员关系及状态（单条 SQL：teams JOIN team_members，active）
  → 验证 Team 角色
  → 如适用则验证项目角色（Phase 03 起）
  → 验证操作权限
  → 验证资源状态（归档/终态，后续阶段）
```

- Handler 负责请求解析和响应映射；Service 负责授权与业务规则；Repository 负责带 Team 约束的数据查询。
- 不允许先按资源 ID 查询出其他团队的数据，然后在内存中决定是否拒绝。
- 团队详情/成员等业务的 membership 校验对 ROOT 同样生效：ROOT 不默认绕过团队业务数据授权；平台级“查看所有团队”能力通过显式管理接口（`/api/v1/admin/teams`）实现并受平台角色约束。未来如需紧急跨团队管理操作，必须设计明确、受限、可审计的例外机制，不在普通业务接口中隐式放行（本阶段不实现例外机制）。

### 授权响应映射

| 情形 | HTTP | 错误码 |
| --- | --- | --- |
| 未认证（无/无效/过期/已撤销会话） | 401 | `unauthorized` |
| 已认证但无该 Team 访问权（含资源不存在） | 404 | `not_found` |
| 有 Team 访问权但操作权限不足 | 403 | `forbidden` |
| 状态冲突（重复成员、过期邀请、最后 owner 等） | 409 | `conflict` |
| 参数非法 | 400 / 422 | `bad_request` / `validation_failed` |
| 登录失败限流 | 429 | `rate_limited` |

- 404 统一措辞，不区分“不存在”与“无权访问”，避免泄漏其他 Team 资源存在性。
- 授权失败（403/404 团队访问拒绝）写入安全审计 `authz.denied`，不含敏感载荷。

### ROOT 与平台角色

- ROOT 由不可变内部 UUID + `users.system_root` 标记 + 部分唯一索引（`WHERE system_root`）保证唯一。
- 专用引导命令 `nexora-bootstrap`：交互式设置密码，无默认密码、不硬编码；并发引导由唯一索引保证只有一个 ROOT；完成后重复引导安全拒绝；初始化写入专门审计事件。
- 不得通过用户名、邮箱或昵称判断 ROOT；`waiting` 仅是默认初始用户名标识。普通接口不得修改 `system_root`；恢复流程不得通过更改用户名实现（本阶段不实现恢复流程，未来须走专用受控程序）。
- 平台角色仅 `platform_admin`，由 ROOT 通过专用管理接口授予/撤销；团队 owner/admin 不映射为平台角色，不能自我提权。
- ROOT 与平台管理员可创建普通账号、查看平台团队列表；ROOT 可撤销任意用户会话。

### 操作审计

- 关键操作必须记录：`actor_id`、`action`、`target_type`、`target_id`、`team_id`（适用时）、`request_id`、操作时间、必要的前后状态及原因（`details` jsonb）。
- 权限变更与审计事件在同一数据库事务中完成；`audit_events` 追加写，数据库触发器禁止 UPDATE/DELETE。
- 禁止记录密码、Cookie、原始会话令牌等敏感内容；登录失败审计仅记录用户名与原因类别。

### 并发与完整性（数据库约束 + 事务 + 行锁）

- 重复成员关系：`(team_id, user_id)` 主键。
- 越权授予角色：Service 层规则（admin 不能授予 owner、不能变更 owner 成员）+ 集成测试。
- 最后 owner 保护：数据库触发器 `team_members_last_owner_guard` 拒绝使 Team 失去最后一名 active owner 的 UPDATE/DELETE；Service 在成员/角色变更前对 `teams` 行 `SELECT ... FOR UPDATE`，串行化同 Team 并发变更，保证触发器计数在并发下正确。
- 邀请约束：同一 `(team_id, invited_user_id)` 仅一条 pending（部分唯一索引）；接受时行锁 + 状态/有效期/接受人身份校验；只能邀请为 admin/member，owner 只能经创建或 owner 角色变更产生。
- 会话令牌仅存 SHA-256 摘要；过期/撤销在服务端判定。

### 新增业务规则清单（非历史决策）

1. 不开放匿名公众注册；账号来源 = ROOT 引导 + 授权创建 + 内部邀请（见 PRD V1.0）。
2. 邀请加入制：成员加入必须经邀请接受流程，不允许仅凭任意用户 ID 直接加入。
3. 邀请有效期默认 72 小时，可指定 1–168 小时；过期邀请接受返回 409。
4. 允许多 owner；admin 不能授予 owner、不能移除或变更 owner；owner 可授予 owner。
5. 成员可自我移除（退出团队），受最后 owner 保护约束。
6. 团队创建者自动成为该团队 owner（同事务写入）。
7. 平台账号创建与平台角色管理为 ROOT/平台管理员专用接口；平台角色授予/撤销仅 ROOT。
8. 团队业务接口对非成员（含 ROOT）返回 404；平台全量团队列表走显式管理接口。
9. 本阶段不实现团队信息编辑、团队归档与批量成员操作；批量接口出现时必须逐项校验、越权整体失败且无部分写入。

## 验证要求

- 跨团队行为必须通过真实 PostgreSQL 集成测试验证（两个以上真实测试 Team），复用 testdb 护栏。
- 强制安全测试矩阵见 [Phase 02 实施计划](../../development/phase-02-plan.md) 与 [权限矩阵](../permissions.md)。
## Phase 04 实施细则（2026-11-18）

成果提交严格要求当前任务分配及有效 Team / Project 资格，项目负责人也不自动取得提交权。默认项目负责人及明确授权的有效成员可审核；ROOT、Team owner/admin 不绕过项目资格，提交者禁止自审。授权与撤销追加审计，授权绑定成员资格 epoch，移除/重加不复活旧授权。此增补收紧到实际业务证据边界，不改变方案 B 的多 Team 隔离原则；验证见 [Phase 04 报告](../../development/phase-04-report.md)。
