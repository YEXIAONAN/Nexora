# ADR 0005：金额与进度计算规则

- 状态：分项决策；**进度 Accepted（2026-11-17）**，**金额 Proposed（V2.0 待批准）**
- 日期：2026-10-29

## 金额（Proposed，原提议保留，未批准）

- 存储：最小货币单位 `bigint`（如分），币种单独字段。
- 计算：整数运算；按权重分配时使用“最大余数法”处理舍入，确保合计等于可分配金额。
- 校验：`SUM(allocation) <= total`；最终确认在事务中重新校验。
- 并发：方案使用版本号与行锁，确认操作幂等。
- 人工调整：记录建议值、调整值、原因、操作人、时间与方案版本。

## 进度（Accepted，2026-11-17）

批准来源：产品负责人 Phase 03 正式开发任务（V1.0 方案 B）。原提议日期 2026-10-29 与金额部分保留，不能将本 ADR 整体解释为金额规则已接受。

- 仅结构叶子计权，父节点仅汇总后代叶子，取消叶子排除分子及分母。
- actual_progress 与 effective_progress 分离：pending=0；in_progress=min(actual,79%)；awaiting_review 默认 80%；正式验收有效且绑定当前成果版本的 completed 才可 100%；rejected 不能自动完成，细则留待 Phase 04。
- Phase 03 actual_progress 采用 0–99 的整数百分比；数据库权重采用 1–1,000,000 正整数；累加用任意精度整数，项目/父进度输出基点整数（10000=100%），向下取整到 0.01%。输出附精确分子/分母字符串，可解释且无二进制浮点误差。
- 没有有效叶子的项目为 0%，不自动完成。Phase 03 不存在真实验收操作，项目有效进度无法通过正常业务达到 100%。
- 权重变化只影响当前及未来计算；不可覆盖或追溯重算历史快照。记录 actor、old/new 权重、原因、生效时间、修改前后项目进度。
- 创建、取消、状态/实际进度、结构和权重变化保存追加式项目进度快照，与业务及审计同事务。
- 原提议中“待验收比例可配置”收敛为本阶段固定 80%；配置化须另行产品决定。
- Phase 04 必须重新核实成果版本与验收关系，才能开放 awaiting_review/completed/rejected；不得伪造 submission/review 或仅凭状态/手工进度计为完成。

详见 [Phase 03 设计](../../development/phase-03-design.md)。

## 原进度提议（2026-10-29，历史保留）

以下原文由上方 2026-11-17 进度决策取代，保留决策演进来源；不据此开放旧系数或额外配置。


- 仅叶子任务参与聚合，避免父子重复计权。
- 取消任务从分子与分母剔除。
- 未验收完成不按 100% 计。
- 权重变更保留历史；历史进度快照可用于解释差异。
- 计算函数为纯函数，配套表驱动单元测试。

### 原待确认项（历史）

进度两项已由上述 Accepted 决策解决；金额余额归属仍待批准。

- 待验收任务的默认完成比例（0.8 或其他）。
- 权重变更是否触发历史项目进度重算，或仅影响变更时点之后。
- 舍入后余额的归属规则（留在未分配余额或按规则分配）。


## Phase 04 实施细则（Accepted，2026-11-18）

批准来源：产品负责人 Phase 04 正式任务。rejected 的有效进度保守回到 0%，不删除旧 actual_progress；提交、驳回、补正和验收均追加项目快照，历史快照不重算。待验收固定 80%；完成必须由当前成果版本的实际 approve 记录证明，单独 completed 字符串仍计 0%。父节点根据后代有效叶子汇总，依赖只在当前版本正式通过后解除。取消前置任务不能解除阻塞。精确整数权重算法沿用 Phase 03。

实现和回归证据见 [Phase 04 设计](../../development/phase-04-design.md) / [报告](../../development/phase-04-report.md)，本条不批准金额或贡献规则。


## Phase 06 M1 部分产品批准记录（2026-11-19，保留原 Proposed 历史）

- **产品负责人原话**：“D5 只有人民币然后D9，归档后不允许修改”。该指令只批准指定范围，**不批准 ADR 0005 的整个金额算法**。
- **D5 已批准的币种边界**：V2.0 初版仅 `CNY`，金额最小单位人民币“分”，不接受其他币种，不实现汇率。金额使用 `bigint`、技术最大金额及 API 序列化等细节仍为候选，需与其他奖金治理决策一起冻结。
- **D9 已批准方案 A**：项目一旦归档，奖金模块不得创建、编辑、提交、核定、修订、异议、裁定、通知或收件，只能按照既有权限读取历史。必须由服务端与数据库双重守护；不得放宽已有 Phase 05 的归档门禁。**归档之前若有未结束奖金计划是否拦截归档，仍待产品决定**。
- **未批准**：D1–D4、D6–D8、D10、A1–A5，以及 D5 剩余金额技术细节；金额总政策状态继续 **Proposed**。本记录是决策增量，不代表 Schema v8、金额 API 或正式发布已获准。
- 具体决策范围参见 [Phase 06 M1 产品决策稿](../../development/phase-06-m1-product-decisions.md)（含签署与待批边界）。


### M1 Final Fix 后发产品决定（2026-11-19）

此前 D9/A“归档后奖金只读”已由产品负责人基于学校奖金延迟发放场景变更为 **D9/B**：归档项目的原任务、成果、贡献记录仍不可修改，但独立奖金域可在归档后新增**真实不同的资金批次**、核定金额并追加新版本修订。**D1/A1**：同一项目允许多个真实奖金批次，正式贡献确认可跨批次合法复用，批次内不可重复引用；资金批次自身应具有独立来源标识和防重约束。**D5 继续仅 CNY/分**。

用户明确授权开展 Phase 06 M2 Schema v8 的独立工程研发；未明确批准的金额算法、资格与核定细节仍 Proposed，不允许未经授权合并、发布或迁移运行中的数据库。该段覆盖旧 D9/A 的业务结论，保留历史记录。
