# 产品需求与业务规则

## 定位

Nexora 是团队内部工程管理平台，核心链路：

```text
项目 → 三级任务 → 成果提交 → 验收 → 贡献核定 → 奖金分配方案 → 归档
```

不是即时聊天、社交、支付、代码托管或通用审批系统。

## 角色

| 层级 | 角色 | 说明 |
| --- | --- | --- |
| 平台 | ROOT | 唯一最高权限主体，独立于业务身份 |
| 平台 | 平台管理员 | 平台级管理，不得获得 ROOT 身份 |
| 平台 | 普通用户 | 通过团队成员关系获得业务权限 |
| 团队 | 所有者 / 管理员 / 成员 | 团队内角色，不可提升为平台角色 |
| 项目 | 项目负责人 / 参与者 | 受团队访问权限约束 |

ROOT 初始身份标识为 `waiting`，但该名称不可作为授权依据。授权依据必须是不可被业务操作修改的内部用户 ID 与系统级 ROOT 标记。ROOT 引导流程不得写入默认密码。

## 团队与资格

必须区分三个概念：

1. **团队成员身份**：能否访问团队资源。
2. **参赛/项目参与资格**：能否出现在特定项目或赛事名单中。
3. **奖金分配资格**：能否进入某次奖金分配。

加入团队不等于自动获得所有奖金分配资格。

## 项目

- 项目属于唯一团队，具有负责人、参与成员、状态、时间计划、里程碑与归档状态。
- 项目归档后只读；更正必须通过受控修订流程形成新版本或更正记录。
- 项目进度由任务权重聚合计算，不接受前端手工百分比。

## 三级任务

- 最多三级：一级 → 二级 → 三级；禁止更深层级。
- 每个任务有唯一负责人、多个协作者、优先级、计划开始/截止时间、工作量权重、前置依赖。
- 禁止循环父子关系、跨项目挂接、超过三级。
- 删除父任务不得破坏历史记录；业务上优先取消或归档。

## 任务状态机

状态：`待开始 → 进行中 → 待验收 → 已完成`，另有 `已驳回`、`已取消`。

合法转换（Phase 2 实现）：

| 从 | 到 | 说明 |
| --- | --- | --- |
| 待开始 | 进行中、已取消 | 开始执行或取消 |
| 进行中 | 待验收、已取消 | 提交成果后进入验收 |
| 待验收 | 已完成、已驳回 | 验收通过或驳回 |
| 已驳回 | 进行中、待验收、已取消 | 修正后重新提交 |
| 已完成 | — | 终态 |
| 已取消 | — | 终态，不得视为完成 |

每次转换记录操作人、时间、前后状态、原因与关联成果/验收记录。

## 前置依赖

- 禁止循环依赖与跨项目依赖。
- 依赖未完成时任务处于阻塞状态。
- 有权限的负责人可忽略依赖，但必须填写原因并写审计日志。

## 进度计算

```text
项目进度 = Σ(叶子任务权重 × 叶子任务完成比例) / Σ(叶子任务权重)
```

规则：

- 仅叶子任务参与聚合，避免父子重复计权。
- `完成比例`：已验收完成 = 1；待验收 = 按提交比例（默认 0.8，可配置）；进行中按实际进度；未开始 = 0。
- 已取消任务从分母中剔除。
- 未验收完成的任务不计为 100%。
- 权重变更保留历史，并记录对进度的影响时点。

具体系数在 Phase 2 实现前以 ADR 固化，并配套单元测试。

## 成果与验收

- 提交成果与验收完成是两个独立动作。
- 成果形式：文字说明、附件、外部链接、Git 提交/PR 地址。
- 验收人必须有权限，操作包括通过、驳回、意见与时间。
- 成果修改后必须形成新版本，旧验收结论不得沿用。

## 贡献核算

- 贡献依据已验收成果，而非任务数量、代码行数或在线时长。
- 记录：任务、成员、成果说明、份额、核定人、核定时间、调整原因与前后值。
- 状态：原始记录 → 待核定 → 已确认 → 修订版本。
- 未验收数据只能作为过程记录，不进入正式核算。
- 修订不得覆盖历史，必须保留版本。

## 奖金分配

- 方案关联团队与项目，记录总额、币种、参与资格、事前约定。
- 引入已确认贡献，生成可解释建议，允许授权负责人调整。
- 金额使用最小货币单位整数或 `numeric`，明确舍入规则。
- 分配合计不得超过可分配金额；零贡献、无资格与未分配余额必须显式处理。
- 最终确认需校验合计，避免重复结算。
- 系统只核算与记录，不执行真实支付。

## 归档与导出

- 归档项目只读，历史贡献、奖金与审计记录可查询。
- 导出支持 Excel、PDF、ZIP，并按权限过滤；导出接口不得绕过团队隔离。
