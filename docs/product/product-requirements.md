# V1.0 正式需求（2026-11-17 批准）

## 定位

Nexora V1.0 是面向 ZERO_R 等小型研发团队的内部工程管理平台，以项目、任务、成果提交、审核验收和历史留痕为核心，底层支持多个独立 Team。

关键目标：

- 一个用户可以加入多个 Team。
- 同一用户在不同 Team 中具有独立角色。
- 不同 Team 之间数据隔离。
- 首版优先满足 ZERO_R 的工作场景。
- 不因为 UI 初期只有单 Team 视角而硬编码单团队。
- 为未来贡献与奖金核算保留可靠业务证据。

## 版本范围

### V1.0（当前交付版本）

- 用户认证与会话
- ROOT 安全初始化
- Team、成员与独立角色
- 平台与团队权限
- 项目与三级任务
- 任务状态机、依赖
- 成果提交与版本管理
- 验收、驳回、重新提交
- 操作审计

### V1.1（规划）

- 贡献核算
- 贡献修订及统计

### V2.0（规划）

- 奖金方案与分配
- 高级可视化
- 完整多团队管理体验
- 通知与导出

V1.1 与 V2.0 属于当前产品规划，保留未来扩展方案，不在 Phase 02 开发。

## 账号与注册策略（Phase 02 默认安全实施）

- 内部团队平台，**不开放匿名公众注册**。
- 账号来源仅限三条受控通道：
  1. ROOT 安全初始化：交互式命令，无默认密码，并发安全，重复引导安全拒绝；
  2. 授权账号创建：ROOT 或平台管理员通过管理接口创建普通账号；
  3. 受控成员邀请：针对已存在账号的内部邀请，具备授权、有效期与接受人身份约束，不要求邮件投递系统。
- `waiting` 仅是 ROOT 初始化的默认用户名标识，不构成特权依据；任何普通账号使用 `waiting` 名称都不能获得 ROOT 能力（安全测试必须覆盖）。
- 本策略是 2026-11-17 随方案 B 批准新增的业务规则，在 ADR 0004 实施细则中明确列出，不是历史决策。

# V2.0 长期产品规划（原始需求基线，历史保留）

> 以下为 V2.0 原始需求全文（仅文末“实现状态”表随时间更新），作为长期产品规划与历史决策记录保留。V1.0 缩围不删除这些需求；多 Team 与独立角色设计仍是长期约束，并已在 V1.0 的数据与授权层先行落地（方案 B）。

## 定位

Nexora 是团队内部工程管理平台，核心链路：

```text
项目 → 三级任务 → 成果提交 → 验收 → 贡献核定 → 奖金分配方案 → 归档
```

不是即时聊天、社交、支付、代码托管或通用审批系统。

## 角色

| 层级 | 角色 | 说明 |
| --- | --- | --- |
| 平台 | ROOT | 唯一最高权限主体，独立于业务身份 |
| 平台 | 平台管理员 | 平台级管理，不得获得 ROOT 身份 |
| 平台 | 普通用户 | 通过团队成员关系获得业务权限 |
| 团队 | 所有者 / 管理员 / 成员 | 团队内角色，不可提升为平台角色 |
| 项目 | 项目负责人 / 参与者 | 受团队访问权限约束 |

ROOT 初始身份标识为 `waiting`，但该名称不可作为授权依据。授权依据必须是不可被业务操作修改的内部用户 ID 与系统级 ROOT 标记。ROOT 引导流程不得写入默认密码。

## 团队与资格

必须区分三个概念：

1. **团队成员身份**：能否访问团队资源。
2. **参赛/项目参与资格**：能否出现在特定项目或赛事名单中。
3. **奖金分配资格**：能否进入某次奖金分配。

加入团队不等于自动获得所有奖金分配资格。

## 项目

- 项目属于唯一团队，具有负责人、参与成员、状态、时间计划、里程碑与归档状态。
- 项目归档后只读；更正必须通过受控修订流程形成新版本或更正记录。
- 项目进度由任务权重聚合计算，不接受前端手工百分比。

## 三级任务

- 最多三级：一级 → 二级 → 三级；禁止更深层级。
- 每个任务有唯一负责人、多个协作者、优先级、计划开始/截止时间、工作量权重、前置依赖。
- 禁止循环父子关系、跨项目挂接、超过三级。
- 删除父任务不得破坏历史记录；业务上优先取消或归档。

## 任务状态机

状态：`待开始 → 进行中 → 待验收 → 已完成`，另有 `已驳回`、`已取消`。

合法转换（Phase 2 实现）：

| 从 | 到 | 说明 |
| --- | --- | --- |
| 待开始 | 进行中、已取消 | 开始执行或取消 |
| 进行中 | 待验收、已取消 | 提交成果后进入验收 |
| 待验收 | 已完成、已驳回 | 验收通过或驳回 |
| 已驳回 | 进行中、待验收、已取消 | 修正后重新提交 |
| 已完成 | — | 终态 |
| 已取消 | — | 终态，不得视为完成 |

每次转换记录操作人、时间、前后状态、原因与关联成果/验收记录。

## 前置依赖

- 禁止循环依赖与跨项目依赖。
- 依赖未完成时任务处于阻塞状态。
- 有权限的负责人可忽略依赖，但必须填写原因并写审计日志。

## 进度计算

```text
项目进度 = Σ(叶子任务权重 × 叶子任务完成比例) / Σ(叶子任务权重)
```

规则：

- 仅叶子任务参与聚合，避免父子重复计权。
- `完成比例`：已验收完成 = 1；待验收 = 按提交比例（默认 0.8，可配置）；进行中按实际进度；未开始 = 0。
- 已取消任务从分母中剔除。
- 未验收完成的任务不计为 100%。
- 权重变更保留历史，并记录对进度的影响时点。

具体系数在 Phase 2 实现前以 ADR 固化，并配套单元测试。

## 成果与验收

- 提交成果与验收完成是两个独立动作。
- 成果形式：文字说明、附件、外部链接、Git 提交/PR 地址。
- 验收人必须有权限，操作包括通过、驳回、意见与时间。
- 成果修改后必须形成新版本，旧验收结论不得沿用。

## 贡献核算

- 贡献依据已验收成果，而非任务数量、代码行数或在线时长。
- 记录：任务、成员、成果说明、份额、核定人、核定时间、调整原因与前后值。
- 状态：原始记录 → 待核定 → 已确认 → 修订版本。
- 未验收数据只能作为过程记录，不进入正式核算。
- 修订不得覆盖历史，必须保留版本。

## 奖金分配

- 方案关联团队与项目，记录总额、币种、参与资格、事前约定。
- 引入已确认贡献，生成可解释建议，允许授权负责人调整。
- 金额使用最小货币单位整数或 `numeric`，明确舍入规则。
- 分配合计不得超过可分配金额；零贡献、无资格与未分配余额必须显式处理。
- 最终确认需校验合计，避免重复结算。
- 系统只核算与记录，不执行真实支付。

## 归档与导出

- 归档项目只读，历史贡献、奖金与审计记录可查询。
- 导出支持 Excel、PDF、ZIP，并按权限过滤；导出接口不得绕过团队隔离。
